# النسخ الاحتياطي المشفّر لـ classi-staging (workflow: "Staging backup")

**الحالة 20/11/2026:** جاهز ومختبر على بيانات وهمية فقط (42 فحصًا محليًا + `backup-drill` في CI). لم يُشغَّل على Staging.

## ما يفعله تشغيل واحد

1. يتحقق من الرابط (classi-staging وليس Production)، ومن cluster id = `7702070854497379551`، ومن علامة `staging`.
2. يأخذ نسخة بـ `scripts/db/backup.sh` (قراءة فقط، لقطة pg_dump واحدة للبيانات)، ويتحقق أن لا migration سُجّلت أثناءها.
3. يشفّر الملف بـ age إلى **مفتاحك العام** وإلى **مفتاح مؤقت** يُنشأ داخل التشغيل.
4. يفتح الملف المشفّر نفسه بالمفتاح المؤقت، ثم **يحذف المفتاح المؤقت**، ثم يستعيد النسخة إلى قاعدة PostgreSQL 17 فارغة ومعزولة،
   ويقارن أعداد الصفوف لكل جدول.
5. يحفظ 3 ملفات فقط: الملف المشفّر، وSHA-256، وملخص أرقام بلا بيانات. ثم job ثانٍ بلا أسرار ينزّل الملف المحفوظ ويثبت أنه هو نفسه.

## اختباران مختلفان للاستعادة

| | اختبار المفتاح المؤقت (في كل تشغيل) | اختبار مفتاحك أنت (مرة على الأقل، على جهازك) |
|---|---|---|
| ماذا يثبت | أن **الملف المشفّر نفسه** سليم، ويُفك تشفيره، وأن محتواه يُستعاد كاملًا بالأعداد نفسها | أن **مفتاحك الخاص** يفتح الملف، أي أن النسخة قابلة للاسترجاع بعد انتهاء التشغيل |
| ما لا يثبته | لا يثبت أن مفتاحك العام في GitHub صحيح: خطأ إملائي فيه ينتج ملفًا لا يفتحه أحد | — |
| أين | داخل GitHub Actions، والمفتاح المؤقت يُحذف قبل الاستعادة | على جهازك فقط |
| كيف | تلقائي | `check-backup-key.sh` قبل أول تشغيل (يعطي MATCH)، ثم `open-backup.sh` على أول نسخة تنزّلها |

الملف المشفّر واحد ويحمل «قفلين»: قفل لمفتاحك وقفل للمفتاح المؤقت. يُكسر قفل المؤقت داخل التشغيل لإثبات سلامة الملف، ثم
يُحذف المفتاح المؤقت. بعدها لا يفتح الملف إلا مفتاحك. CI يجرّب الطريقين في كل تشغيل بمفتاح «مالك» تجريبي: تعود الحسابات
الخمسة الوهمية كاملة.

## 1. إنشاء مفتاحك (مرة واحدة، نحو 15 دقيقة، لا يُرسل شيء في المحادثة)

افعل ذلك في مجلد خاص على جهازك، **خارج** OneDrive وGoogle Drive وأي مجلد متزامن.

**أ. ثبّت age:**
- Windows: افتح PowerShell واكتب `winget install FiloSottile.age`، ثم أغلق PowerShell وافتحه من جديد.
- Mac: `brew install age`.

**ب. أنشئ المفتاح:**
```
age-keygen -o classi-backup.key
```
يطبع سطرًا يبدأ بـ `Public key: age1…`. هذا **المفتاح العام**، وانسخه في مكان ما. الملف `classi-backup.key` هو **المفتاح الخاص**.

**ج. احمِ المفتاح الخاص بكلمة مرور:**
```
age -p -o classi-backup.key.age classi-backup.key
```
اختر كلمة مرور قوية (4 كلمات عشوائية أو أكثر) واحفظها في مدير كلمات المرور.

**د. تحقق قبل حذف النسخة غير المحمية:**
```
age -d classi-backup.key.age | age-keygen -y
```
يطلب كلمة المرور، ثم يطبع `age1…`. يجب أن يطابق السطر العام من الخطوة ب حرفًا بحرف.

**هـ. احذف `classi-backup.key`** (غير المحمي)، وأفرغ سلة المحذوفات.

**و. احفظ نسختين من `classi-backup.key.age`:** واحدة في مدير كلمات المرور كمرفق، وواحدة على USB في مكان آمن.
**إذا ضاع الملف أو كلمة مروره فلن تُفتح أي نسخة.** لا ترسله لأحد، ولا تضعه في GitHub أو في المحادثة.

## 2. ضع المفتاح العام في GitHub (أنت، نحو 3 دقائق)

GitHub → المستودع → Settings → Environments → **staging-db**:
1. **Environment variables → Add variable**: الاسم `BACKUP_AGE_RECIPIENTS`، والقيمة سطر `age1…` فقط. هذا متغير وليس سرًا،
   ولا يكفي لفتح أي نسخة.
2. **Environment secrets**: تأكد أن `STAGING_DB_URL` موجود. إن لم يكن، أضفه من Supabase → classi-staging → Connect →
   Session pooler. لا ترسله في المحادثة.
3. **Deployment protection rules**: Required reviewers = أنت.
4. **Deployment branches**: Selected branches = `staging-migrate`.

## 3. التشغيل خطوة بخطوة (كل خطوة بموافقتك)

GitHub يعرض زر «Run workflow» فقط للـ workflows الموجودة في `main`، و`main` لا يحتوي أي workflow. لذلك يبدأ التشغيل
بـ push إلى `staging-migrate` رسالة الـ commit فيه تبدأ بالضبط بـ `[staging-backup] backup classi-staging`. أي push آخر
إلى هذا الفرع يتخطى الـ job تمامًا ولا يطلب أي موافقة.

1. **موافقتك الأولى (أنا أنفّذ):** تقديم `staging-migrate` إلى commit من `v3/dev` نجح عليه CI (fast-forward، بلا دمج).
   هذا لا يشغّل شيئًا: لا workflow يعمل بـ push على هذا الفرع سوى هذا (ويتخطى نفسه)، وVercel لا يبنيه (`vercel.json`).
2. **موافقتك الثانية (أنا أنفّذ):** commit فارغ على `staging-migrate` رسالته `[staging-backup] backup classi-staging`.
   يبدأ الـ workflow وينتظر.
3. **أنت:** GitHub → Actions → التشغيل «Staging backup» → **Review deployments** → `staging-db`.
   - قبل الموافقة تأكد أن commit التشغيل هو الذي أذكره لك.
   - ثم Approve and deploy.
4. **انتظر نحو 5–8 دقائق.** في Summary يجب أن ترى **Staging backup: PASS** مع الحجم وSHA-256، ثم job ثانيًا بنتيجة
   **PASS: the stored copy is the restored one**.
5. **أنت:** في أسفل صفحة التشغيل → Artifacts → نزّل `classi-staging-backup-<رقم>` (ملف zip فيه 3 ملفات)، واحفظه خارج المزامنة.
6. **أنت، مرة واحدة على الأقل:** افتح النسخة بمفتاحك. على Mac أو Git Bash في Windows:
   ```
   age -d classi-backup.key.age | sh scripts/db/open-backup.sh classi-staging-<stamp>.tar.age - مجلد-جديد
   ```
   يطبع: SHA-256 مطابق، وفُتح الملف، وكل الملفات مطابقة، وعدد الجداول والصفوف. لا يطبع بيانات. احذف المجلد بعدها.

إن فشلت أي خطوة: يتوقف التشغيل، ولا يُحفظ شيء، ولا يتغير شيء في Staging. أراجع السجل وأبلغك، ولا أعيد المحاولة دون موافقتك.

## 4. أين تُحفظ النسخة، وكم

| المكان | ما فيه | مدة الاحتفاظ |
|---|---|---|
| GitHub Artifact `classi-staging-backup-<رقم التشغيل>` | الملف المشفّر + SHA-256 + ملخص الأعداد | **3 أيام** عند التشغيل بالـ push (1 أو 3 أو 7 عند التشغيل اليدوي لاحقًا). بعدها يحذفه GitHub تلقائيًا |
| جهازك أو USB (خارج المزامنة) | الملف نفسه بعد تنزيله | **30 يومًا**، أو حتى أسبوع بعد نجاح الخطوة التي أُخذت النسخة من أجلها، ثم احذفه |

المستودع **عام**، فأي مستخدم GitHub مسجّل يستطيع تنزيل الـ Artifact خلال الأيام الثلاثة. لكنه ملف مشفّر (X25519 +
ChaCha20-Poly1305) لا يفتحه أحد بدون مفتاحك وكلمة مروره. وجعل المستودع خاصًا يقصر التنزيل عليك.

## 5. ماذا تُظهر السجلات (المستودع عام)

- **يظهر:** أسماء الخطوات، والمضيف (`…pooler.supabase.com`)، وعدد مفاتيحك (1)، وعدد الجداول والصفوف، والحجم، وSHA-256، وPASS/FAIL.
- **لا يظهر:** أي صف أو قيمة أو اسم زبون، ولا الرابط أو كلمة المرور (السر مقنّع بالكامل، وكلمة المرور مقنّعة وحدها أيضًا).
  رسائل أخطاء القاعدة تُطبع بلا قيم بين علامات تنصيص، وبلا سطور CONTEXT/DETAIL، وبلا `user:password@`.
- **مختبر:** إخراج النجاح والفشل والاتصال الفاشل كلها بلا بيانات وبلا كلمة مرور (`staging_backup_test.sh`).

## 6. ما لا يفعله

- **لا يكتب في Staging:** pg_dump في معاملة READ ONLY، وكل استعلامات السكربت في `begin transaction read only`. وفي CI تُقارن
  بصمة المصدر وأعداد صفوف كل جدول والحسابات قبل النسخ وبعده، وتخرج متطابقة.
- **لا migration ولا نشر:** لا `supabase db push` ولا `link` ولا Vercel في الملف، وفحص آلي في CI يمنع إضافتها.
  و`staging-migrate` معطّل في Vercel.
- لا يغيّر إعدادات GitHub أو Supabase. ملفات الصور في Storage غير مشمولة.

## 7. التكلفة

**صفر:**
- دقائق GitHub Actions مجانية بلا حد للمستودعات العامة على الأجهزة القياسية.
- تخزين الـ Artifacts مجاني للمستودعات العامة.
- قراءة نحو 22 MB من Staging لا تقترب من حصة Supabase.
- age وSupabase CLI مجانيان.

إذا جعلت المستودع خاصًا، تبقى ضمن الحصة المجانية: 2000 دقيقة شهريًا، والتشغيل يستهلك نحو 10 دقائق.

## 8. الاستعادة لاحقًا إلى قاعدة فارغة

```
age -d classi-backup.key.age | TARGET_URL='postgresql://…قاعدة فارغة ليست Production…' sh scripts/db/open-backup.sh classi-staging-<stamp>.tar.age - مجلد-جديد
```

`open-backup.sh` يرفض المجلد الموجود، والمفتاح الخطأ، والملف التالف. و`restore-check.sh` يرفض الإنتاج هدفًا.

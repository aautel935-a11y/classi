# النسخ الاحتياطي المشفّر لـ classi-staging (workflow: "Staging backup")

**الحالة 20/11/2026:** الملفات جاهزة ومختبرة على بيانات وهمية فقط. لم يُشغَّل الـ workflow على Staging الحقيقي.

## ماذا يفعل تشغيل واحد

1. يتحقق من الرابط (classi-staging، وليس Production) ومن cluster id = `7702070854497379551` ومن علامة `staging`.
2. يأخذ نسخة بـ `scripts/db/backup.sh`: schema وdata (public, app_private, auth) وcounts وSHA256SUMS. البيانات كلها من لقطة pg_dump
   واحدة، ويتحقق أن لا migration سُجّلت أثناء النسخ.
3. يشفّر بـ age إلى **مفتاحك العام** وإلى مفتاح مؤقت يُنشأ في التشغيل.
4. يفتح **الملف المشفّر نفسه** بالمفتاح المؤقت، **يحذف المفتاح المؤقت**، ثم يستعيد إلى قاعدة PostgreSQL 17 فارغة ومعزولة داخل
   التشغيل → **PASS** فقط إذا تطابقت أعداد صفوف كل الجداول.
5. يحفظ 3 ملفات فقط: الملف المشفّر، وSHA-256، وملخص أرقام بلا بيانات. job ثانٍ بلا أسرار ينزّل الملف المحفوظ ويثبت أنه هو نفسه.

## المراجعة الأمنية النهائية (20/11)

| السؤال | الجواب | الدليل |
|---|---|---|
| هل يمر مفتاحك الخاص بـ GitHub؟ | **لا، أبدًا.** GitHub يعرف المفتاح العام فقط (`age1…`)، وهو يكفي للتشفير ولا يفتح شيئًا. | السكربت يرفض أي `AGE-SECRET-KEY` في `BACKUP_AGE_RECIPIENTS`، وGitleaks يفحص كل التاريخ بقاعدة age |
| المفتاح المؤقت في التشغيل؟ | يُنشأ في مجلد مؤقت خاص (700)، ولا يُطبع، ويُحذف قبل الاستعادة. قبل الحفظ يتحقق السكربت أن مجلد الإخراج فيه 3 ملفات فقط ولا مفتاح خاص | `staging-backup.sh` + الاختبار المحلي 37/37 |
| ماذا تُظهر السجلات والملخص؟ | أسماء الخطوات، والمضيف، وعدد الجداول والصفوف، والحجم، وSHA-256. رسائل أخطاء القاعدة تُطبع **بلا قيم** وبلا سطور CONTEXT/DETAIL | الاختبار يتحقق أن الإخراج بلا بيانات، حتى عند الفشل |
| هل يغيّر شيئًا في Staging؟ | **لا.** pg_dump يعمل في معاملة READ ONLY، وكل استعلامات السكربت في `begin transaction read only`. لا يوجد في الـ workflow أي push أو نشر أو migration (فحص آلي في CI) | CI `backup-drill`: بصمة المصدر وأعداد صفوف كل جدول والحسابات متطابقة قبل النسخ وبعده |
| هل يمكن استعادة النسخة لاحقًا، لا داخل التشغيل فقط؟ | **نعم**، بشرطين: أن تنزّلها قبل انتهاء مدة الاحتفاظ، وأن يكون مفتاحك العام في GitHub مطابقًا لمفتاحك الخاص (يثبته `check-backup-key.sh`) | CI يجرّب الطريق كاملًا في كل تشغيل: `open-backup.sh` بمفتاح «المالك» إلى قاعدة جديدة فارغة، وتعود الحسابات الخمسة |
| من يستطيع **تشغيل** الـ workflow؟ | من لديه صلاحية كتابة في المستودع. لكن الوصول إلى `STAGING_DB_URL` لا يتم إلا بعد **موافقتك** على البيئة `staging-db`، ومن الفرع `staging-migrate` فقط | إعدادات البيئة (تتحقق منها أنت، فأدواتي لا تستطيع قراءتها) |
| من يستطيع **تنزيل** النسخة؟ | المستودع **عام**، فأي مستخدم GitHub مسجّل يستطيع تنزيل الـ Artifact. لكنه **ملف مشفّر** لا يفتحه أحد بدون مفتاحك الخاص (X25519 + ChaCha20-Poly1305)، ويحذفه GitHub بعد يوم أو 3 أو 7 أيام | جعل المستودع خاصًا يقصر التنزيل عليك (بند في PENDING_APPROVAL) |
| خطر متبقٍ | من يملك صلاحية الكتابة يستطيع تعديل السكربت على `staging-migrate` قبل تشغيل توافق عليه. **وافق فقط إذا كان commit التشغيل هو المذكور في تقريري**، وأنت المالك الوحيد حاليًا | — |

تقوية اختيارية لاحقًا (تحتاج موافقتك لأنها تغيير على Staging): دور قاعدة للقراءة فقط بدل `postgres` في `STAGING_DB_URL`.

## الإعداد على جهازك (مرة واحدة، نحو 15 دقيقة)

**1. ثبّت age.** في Windows افتح PowerShell واكتب `winget install FiloSottile.age`. في Mac اكتب `brew install age`.

**2. أنشئ المفتاح** في مجلد خاص غير متزامن مع Drive أو OneDrive:
```
age-keygen -o classi-backup.key
```
يطبع سطرًا مثل `Public key: age1…`، وهذا هو المفتاح **العام**. الملف `classi-backup.key` هو المفتاح **الخاص**.

**3. احمِ المفتاح الخاص بكلمة مرور** (موصى به):
```
age -p -o classi-backup.key.age classi-backup.key
```
اختر كلمة مرور قوية واحفظها في مدير كلمات المرور. بعد التأكد من الخطوة 5، احذف `classi-backup.key` غير المحمي.

**4. احفظ نسختين من `classi-backup.key.age`:** واحدة في مدير كلمات المرور (مرفق أو ملاحظة آمنة)، وواحدة على USB تحفظه في
مكان آمن. **إذا ضاع المفتاح الخاص فلن تُفتح أي نسخة.** لا ترسله لأحد، ولا تضعه في GitHub أو في المحادثة.

**5. ضع المفتاح العام في GitHub:** Settings → Environments → **staging-db** → Variables → New variable
→ الاسم `BACKUP_AGE_RECIPIENTS`، والقيمة `age1…` (السطر العام فقط).

**6. تأكد أن المفتاحين متطابقان** (في Git Bash أو Mac، من مجلد المستودع):
```
age -d classi-backup.key.age | sh scripts/db/check-backup-key.sh - 'age1…'
```
يجب أن تظهر **MATCH**. إن ظهر NO MATCH فصحّح المتغير في GitHub.

**7. في البيئة staging-db:** تأكد من وجود السر `STAGING_DB_URL`، ومن أن Required reviewers = أنت، وأن الفروع المسموحة = `staging-migrate` فقط.

## التشغيل (يحتاج موافقتك في كل مرة)

1. أطلب منك الموافقة على دفع الملفات إلى `staging-migrate` (مرة واحدة).
2. Actions → Staging backup → Run workflow (الفرع staging-migrate) → اكتب `backup classi-staging` → اختر مدة الاحتفاظ.
3. وافق على البيئة staging-db **بعد التأكد أن commit التشغيل هو المذكور في تقريري**.
4. النتيجة في Summary: PASS، والحجم، وSHA-256.

## الاحتفاظ

| أين | ماذا | المدة |
|---|---|---|
| GitHub Artifact `classi-staging-backup-<run id>` | الملف المشفّر + SHA-256 + الملخص | 1 أو 3 أو 7 أيام (الافتراضي 3) |
| جهازك أو USB (خارج المزامنة) | نسخة الملف المشفّر نفسه، تنزّلها من صفحة التشغيل | 30 يومًا، أو حتى أسبوع بعد نجاح الخطوة التي أخذت النسخة من أجلها |

الملف المشفّر آمن في أي مكان ما دام مفتاحك الخاص محميًا. لا تفتحه إلا عند الحاجة، واحذف المجلد المفتوح بعد الاستعمال.

## الاستعادة لاحقًا

```
# تحقق وافتح فقط (يطبع الأعداد، بلا بيانات)
age -d classi-backup.key.age | sh scripts/db/open-backup.sh classi-staging-<stamp>.tar.age - مجلد-جديد
# أو استعد أيضًا إلى قاعدة فارغة ليست Production
age -d classi-backup.key.age | TARGET_URL='postgresql://…' sh scripts/db/open-backup.sh classi-staging-<stamp>.tar.age - مجلد-جديد
```

السكربت يتحقق من SHA-256، ويفك التشفير، ويتحقق من كل ملف داخلي، ثم يستعيد ويقارن الأعداد. يرفض المجلد الموجود والمفتاح الخطأ
والملف التالف.

# تحليل أمني: الصور غير المعتمدة (المنتظرة والمرفوضة)

**التاريخ:** 3/11/2026. **تحليل فقط**، لا تغيير في الكود أو قاعدة البيانات.

## الوضع الحالي

- كل الصور في bucket واحد **عام** (`avatars`)، وفي مجلد صاحبها، **باسم فريد لكل رفع**: `teacher-<وقت>-<8 أحرف عشوائية>.jpg`.
- **صورة المعلم أو المعهد الجديدة:**
  - تُرفع مباشرة إلى الـ bucket العام؛
  - يُحفظ رابطها في `pending_changes` بانتظار المدير؛
  - التطبيق يعرض للأهل الصورة المعتمدة فقط.
- **المرفوضة:** يبقى ملفها حتى زيارة المالك التالية بعد دقيقتين على الأقل، فيحذفه التنظيف.
- **الصورة الشخصية** (طالب، ولي أمر): بلا مراجعة، وتُنشر مباشرة.
- **الرفع** بلا `cacheControl`، فتُطبَّق القيمة الافتراضية لـ Supabase. أعتقد أنها ساعة، ولم أتحقق منها هنا. الـ CDN يحفظ نسخة من أي رابط طُلب.

## 1. هل يمكن فتح الصورة قبل موافقة المدير برابط عام؟

**نعم.**
- الملف في bucket عام من لحظة الرفع، ورابطه العام يعمل فوراً، وسجلات staging تُظهر ذلك: `GET .../public/avatars/<teacher>/teacher-....jpg` ← 200 والصورة ما زالت منتظرة.
- **من يعرف الرابط اليوم:**

| | الآن | بعد migration ‏`avatars: read own` |
|---|---|---|
| المالك | ✓ | ✓ |
| المدير (بطاقة المراجعة) | ✓ | ✓ |
| أي مستخدم مسجّل عبر `pending_changes` | ✗، أُغلق في `20261103010000` | ✗ |
| **أي شخص عبر السرد (list)** | **✓ الثغرة الأساسية** | ✗ |
| التخمين | عملياً لا: ‏8 أحرف عشوائية ≈ 41 bit، ولا سرد | لا |
| من تسرّب إليه الرابط (مشاركة، سجلّ متصفح) | ✓ | ✓ |

- **المرفوضة** تبقى قابلة للفتح برابطها حتى تُحذف، ثم قد يبقى الـ CDN يقدّم نسخة حتى انتهاء مدة الكاش، كما ظهر في S10.

## 2. هل تقييد LIST وحده كافٍ؟

- **كافٍ لإغلاق الهجوم الواقعي** وهو الحصر: لا أحد يستطيع اكتشاف صور غيره، والاسم العشوائي يمنع التخمين. هذا يرفع الخطر من «أي زائر» إلى «من حصل على الرابط بطريقة أخرى».
- **غير كافٍ إن كان المطلوب** «لا تُرى أي صورة قبل موافقة المدير إطلاقاً»، أو منع **إساءة الاستخدام**:
  - يستطيع حساب معلم رفع صورة مسيئة ومشاركة رابطها خارج Classi، فتعمل استضافةً عامة على نطاق المشروع حتى الرفض والحذف، ثم مدة الكاش.
  - الصورة المرفوضة تبقى متاحة بين الرفض وزيارة المالك التالية.

## 3. هل نحتاج bucket خاصاً للصور المنتظرة؟

**التصميم المقترح (للمرحلة القادمة، بعد موافقتك):**
1. **bucket خاص** `photos-pending`، يرفع إليه المالك ويقرأ ويحذف في مجلده فقط، والمدير يقرأ عبر روابط موقّعة.
2. **الرفع:** صورة المعلم أو المعهد تُرفع إلى الـ bucket الخاص، ويُحفظ في `pending_changes` **مسار** الملف لا رابطه العام.
3. **المدير:** بطاقة المراجعة تعرض **رابطاً موقّعاً قصير الأجل** (مثلاً 5 دقائق) يُولَّد على الخادم بعد التحقق من أنه مدير.
4. **الموافقة:** على الخادم، **نسخ** الملف إلى الـ bucket العام باسم فريد جديد، ثم حفظ الرابط العام، ثم حذف الأصل الخاص. **الرفض:** حذف الملف الخاص فوراً.
5. **الصور الشخصية:** تبقى عامة كما هي. ويمكن لاحقاً، إن رغبتَ لأسباب خصوصية القاصرين، جعلها خاصة بروابط موقّعة، لكنه تغيير أكبر لأنها تُعرض في صفحات كثيرة.

**ما يتطلبه ذلك:**
- **نسخ ملف بين bucketين** يحتاج صلاحية خادم: إما مفتاح service role في server action للمدير، أو Edge Function. دالة SQL وحدها لا تنقل ملفات التخزين.
- **migration:** bucket جديد وسياساته، وتعديل `photo_owner_guard` ليقبل مسار الـ bucket الخاص في `pending_changes`.
- **كود التطبيق:**
  - `PhotoUpload`: وجهة الرفع؛
  - `savePhotoAction`: التحقق من المسار؛
  - بطاقة المراجعة: روابط موقّعة؛
  - `admin_review`: إلى server action يجمع القرار والنسخ؛
  - `tidyPhotos`: تنظيف bucketين.
- **اختبارات:** قاعدة البيانات (السياسات)، والوحدات، وS10b بالدورة الجديدة.

## 4. الأثر على التطبيق والأداء والتكلفة

| | تقييد LIST وحده (جاهز) | bucket خاص للمنتظرة |
|---|---|---|
| كود التطبيق | لا تغيير | متوسط: 5 مواضع + مسار موافقة على الخادم |
| أداء صفحات الأهل | بلا أثر | بلا أثر: الصور المعتمدة عامة ومخزّنة في الـ CDN كما هي |
| أداء المدير | بلا أثر | رابط موقّع لكل صورة منتظرة، وهي قليلة، بلا كاش. أثر ضئيل |
| الأسرار | لا جديد | مفتاح service role على الخادم (Vercel)، أو Edge Function |
| التكلفة | صفر | شبه صفر: نسخة مؤقتة لكل صورة منتظرة، وعملية نسخ عند الموافقة |
| المخاطر | منخفضة جداً | متوسطة: ترحيل الصور المنتظرة الحالية، ومسار موافقة جديد |
| ما يغلقه | الحصر وتجاوز المراجعة بالسرد | كل ما سبق، **وأي ظهور قبل الموافقة**، والاستضافة المسيئة |

## 5. التوصية

1. **الآن:** migration ‏`avatars: read own`، وهي جاهزة ومختبرة وتغلق الثغرة الأساسية، بلا تغيير كود.
2. **تحسينات صغيرة منخفضة الخطر** (تحتاج تعديل كود، بموافقتك):
   - رفع الصور المنتظرة بمدة كاش قصيرة، تقلل بقاء المرفوضة في الـ CDN؛
   - حذف ملف الصورة المرفوضة لحظة الرفض بدل انتظار زيارة المالك. يحتاج صلاحية خادم، فالأنسب ضمّه إلى البند 3.
3. **قبل الإطلاق العام أو بعده بقليل:** bucket خاص للمنتظرة كما في القسم 3، كمرحلة منفصلة بخطة واختبارات وتطبيق على staging أولاً.
4. **قرار منتج:** هل تبقى الصور الشخصية للطلاب عامة الرابط؟

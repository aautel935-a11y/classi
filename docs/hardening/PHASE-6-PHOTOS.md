# المرحلة 6: إصلاح صور المعلمين والمعاهد (ملف فريد لكل رفع)

**التاريخ:** 3/11/2026
**الفرع:** `hardening/photo-unique-files` = `2c47a6b` (من `hardening/phase6-staging-tests` = `4b4565c`، المنشور على staging).
**الحالة:** مُختبر محلياً وفي CI. **لم يُنشر على Staging** (بانتظار موافقتك). لا تعديل على `main` أو `staging` أو الإنتاج، ولا SQL ولا migrations.

## 1. المشكلة

- كان مسار الصورة ثابتاً لكل حساب (`<user>/teacher.jpg`)، وكل رفع **يكتب فوق الملف نفسه** (`upsert`).
- **النتيجة:** صورة المعلم أو المعهد الجديدة تظهر للأهل **فوراً**، قبل موافقة الإدارة. الرابط المعتمد يشير إلى الملف نفسه الذي استُبدل، فالمراجعة كانت شكلية بالنسبة للصور.
- عند الرفض، كان المحتوى الجديد قد حلّ محل القديم فعلاً.

## 2. الإصلاح

| المتطلب | التنفيذ |
|---|---|
| 1. اسم ملف فريد لكل رفع | `<kind>-<الوقت>-<عشوائي>.jpg` داخل مجلد المالك، **دون كتابة فوق أي ملف** (`upsert: false`). |
| 2. الصورة المعتمدة تبقى حتى الموافقة | الملف المعتمد لا يُمسّ؛ الرابط الجديد ينتظر في `pending_changes` (آلية المراجعة الموجودة). المعلم يرى رسالة: «وصلت الصورة الجديدة للإدارة للمراجعة. تبقى صورتك الحالية ظاهرة للأهل حتى الموافقة». |
| 3. عند الرفض تبقى القديمة | الرفض يمسح التعديل المعلّق فقط؛ الصورة المعتمدة وملفها كما هما. |
| 4. الصلاحيات عند الحذف والاستبدال | المسارات تُبنى على الخادم من الحساب المسجّل فقط، وسياسة التخزين `avatars: delete own` تمنع أي ملف خارج مجلد المستخدم. الحفظ يقبل فقط: مجلد المالك نفسه، اسم ملف من نوع الصورة نفسه، `https`، ومشروع Supabase نفسه. |
| 5. منع تراكم الملفات بأمان | التنظيف يحذف **فقط** ملفات المالك من النوع نفسه التي **ليست** الصورة المعتمدة **ولا** المعلّقة للمراجعة. الملف المستبدَل أو المحذوف يُحذف فوراً؛ أي ملف آخر غير مستعمل (مثل صورة مرفوضة) **بعد دقيقتين على الأقل** من رفعه، حتى لا يُحذف رفع لم يكتمل حفظ رابطه بعد. يعمل بعد الحفظ والإزالة، وبهدوء عند فتح المالك لصفحته. إن تعذّرت قراءة الحالة لا يُحذف شيء. |
| فشل الحفظ بعد الرفع | يُحذف الملف الجديد (لا يستعمله شيء). |

**الملفات:** `lib/photos.ts` (جديد، دوال بحتة)، `app/actions.ts` (`savePhotoAction`، `removePhotoAction`، `tidyPhotosAction`)، `components/PhotoUpload.tsx`.
**لا تغيير** في قاعدة البيانات أو سياسات التخزين أو الإعدادات. الصور القديمة بالاسم الثابت (`teacher.jpg`) تبقى ما دامت معتمدة، وتُنظَّف بعد استبدالها والموافقة على البديل.

## 4. ما بقي (لم يُصلح هنا، يحتاج قرارك)

1. **قاعدة البيانات لا تتحقق من أن رابط الصورة في مجلد صاحبه.** التطبيق يتحقق (`validPhotoUrl`)، لكن من يستدعي الـ API مباشرة يستطيع وضع رابط ملف شخص آخر (من التخزين العام نفسه):
   - صورة الملف الشخصي تُطبَّق فوراً، لأنها لا تخضع للمراجعة.
   - صورة المعلم أو المعهد تذهب للمراجعة.
   - **الحل:** قيد في قاعدة البيانات يطابق المجلد بصاحب الصف. يحتاج **migration** (staging ثم الإنتاج) بموافقتك.
2. **المستخدم المسجّل يقرأ التعديلات المعلّقة للمعلمين والمعاهد الآخرين** (`pending_changes`): الزائر ممنوع، لكن أي حساب مسجّل يقرؤها. خطورة منخفضة. الحل صلاحيات أعمدة أو دالة؛ يحتاج migration.
3. **الصورة المرفوضة تُحذف عند زيارة المالك التالية لصفحته** (بعد دقيقتين على الأقل)، لا لحظة الرفض. المدير لا يملك صلاحية حذف ملفات غيره، وهذا مقصود. الحد الأقصى ملف مرفوض واحد ينتظر لكل نوع.
4. **المسار الكامل** (رفع ← حفظ ← موافقة) لا يُختبر في CI، لأن الحزمة المحلية `http` وقاعدة البيانات تقبل `https` فقط. يُختبر في S10b على Staging المستضاف.

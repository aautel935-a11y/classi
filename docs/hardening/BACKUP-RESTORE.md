# النسخ الاحتياطي والاستعادة

**المبادئ:**
- **النسخ قراءة فقط** من الإنتاج.
- **الاستعادة لا تكون أبداً في مشروع الإنتاج.** السكربتات ترفض معرّف مشروع الإنتاج `rfxhqcagdsuhkjzwbawx` هدفاً.
- لا يُطبع أي سر ولا أي بيانات: فقط أسماء الملفات وعدد الصفوف لكل جدول.

**الوضع الحالي:** الخطة المجانية في Supabase لا تعطي نسخاً تلقائية قابلة للتنزيل، لذلك النسخ اليدوي هو الضمان الوحيد اليوم. خطة Pro تعطي نسخاً يومية لسبعة أيام.

## ما تحويه النسخة وما لا تحويه

| يُحفظ في النسخة | لا يُحفظ، ويُعاد بطريقة أخرى |
|---|---|
| الجداول والدوال والسياسات وكل بيانات التطبيق (`public`) | **ملفات الصور** (bucket `avatars`): تُنسخ منفصلة (القسم 3) |
| الحسابات (`auth.users` وما يتبعها) | **المهام المجدولة** (pg_cron): `scripts/db/cron-jobs.sql` |
| `app_settings` و`app_secrets` (فيها أسرار، فاحمِ الملفات) | **إعدادات Supabase Auth** (Captcha، hook، الروابط): يدوياً من `LAUNCH-CHECKLIST.md` §3 |
| | **قواعد التخزين** (bucket وسياساته): `scripts/db/storage-setup.sql` |
| | **متغيرات Vercel**: تبقى في Vercel |

## 1. أخذ نسخة (قراءة فقط)

```sh
# على جهازك، خارج مجلد المشروع. الرابط من Supabase ← Project Settings ← Database ← Connection string (Session pooler)
DB_URL='postgresql://postgres.<ref>:<password>@<host>:5432/postgres' sh scripts/db/backup.sh ~/ClassiBackups
```

**الناتج:** مجلد `classi-backup-<وقت>` فيه:
- `roles.sql` و`schema.sql` و`data.sql`؛
- `counts.txt`: عدد الصفوف لكل جدول، دون أي محتوى؛
- `SHA256SUMS`.

**يستعمل Supabase CLI إن وُجد** (الطريقة التي توصي بها Supabase)، وإلا `pg_dump`.

**الحماية:**
- يرفض الحفظ داخل مجلد المشروع، حتى لا تُرفع النسخة إلى GitHub.
- يضبط الصلاحيات على المالك فقط (`700`/`600`).

**احتفظ بالنسخة:**
- خارج المجلدات المتزامنة العامة؛
- مشفّرة إن أمكن (مثل قرص مشفّر)؛
- واحذفها عند انتهاء الحاجة، فهي تحوي بيانات شخصية وأسراراً.

## 2. تجربة الاستعادة (إلزامية قبل الإطلاق)

**الهدف:** مشروع Supabase جديد فارغ، أو مشروع Staging قبل تعبئته. **لا يكون أبداً الإنتاج.**

```sh
TARGET_URL='postgresql://postgres.<ref غير الإنتاج>:<password>@<host>:5432/postgres' \
  sh scripts/db/restore-check.sh ~/ClassiBackups/classi-backup-<وقت>
# ثم في محرر SQL للمشروع الهدف:
#   scripts/db/storage-setup.sql   (bucket الصور وقواعده)
#   scripts/db/cron-jobs.sql       (المهام المجدولة السبع)
```

**ما يتحقق منه السكربت:**
- سلامة الملفات (checksums)؛
- الاستعادة في معاملة واحدة: كل شيء أو لا شيء؛
- **تطابق عدد الصفوف في كل جدول** مع `counts.txt`.

**الخيار `DATA_ONLY=1`:** للهدف الذي طُبّقت عليه الـ migrations مسبقاً. يُفرغ جداول `public` في الهدف، ثم يحمّل البيانات.

### ما جُرّب

| أين | ماذا | النتيجة |
|---|---|---|
| Postgres محلي، 20,000 حساب و200,000 حجز اصطناعية | نسخ (`pg_dump`) ← استعادة كاملة في قاعدة فارغة | PASS: 39 جدولاً بعدد الصفوف نفسه. بصمات نتائج الدوال (56) مطابقة للأصل. السياسات 61 = 61 بعد `storage-setup.sql` |
| نفسه | استعادة البيانات فقط في قاعدة عليها كل الـ migrations | PASS: 39 جدولاً |
| CI: Supabase محلي كامل، بعد اختبارات المتصفح | نسخ بـ **Supabase CLI** ← `db reset` ← استعادة ← المهام المجدولة | PASS: 64 جدولاً، 7 مهام مجدولة |
| الحماية | هدف = مشروع الإنتاج؛ نسخة داخل المستودع | رُفض الاثنان |
| **الإنتاج** | — | **لم يُجرَّب.** يحتاج موافقتك ورابط القاعدة منك. تشغيله على جهازك هو الأفضل، فلا تخرج البيانات منه |

## 3. ملفات الصور

**النسخ:** Supabase CLI (تجريبي):
```sh
supabase storage cp -r ss:///avatars ./avatars --experimental --linked
```
أو من لوحة Storage يدوياً إن كانت قليلة.

**الاستعادة:** رفع المجلد إلى bucket `avatars` في المشروع الجديد.

**تنبيه:** روابط الصور في قاعدة البيانات تحوي معرّف مشروع الإنتاج، والقيود تفرض ذلك الشكل. في حالة **انتقال دائم** إلى مشروع آخر يلزم تحديث الروابط:
```sql
update teachers set photo_url = replace(photo_url, '<ref قديم>', '<ref جديد>') where photo_url like '%<ref قديم>%';
```
ومثلها لـ `institutes.logo_url` و`profiles.avatar_url`. تجربة الاستعادة وحدها لا تحتاج هذا.

## 4. متى تؤخذ النسخ

- **قبل أي نشر على الإنتاج:** مباشرة قبل المرحلة 3 من `LAUNCH-CHECKLIST.md` §8.
- **أسبوعياً حتى الترقية إلى Pro:** يدوياً، أو كمهمة مجدولة على جهازك.
- **بعد الترقية إلى Pro:** النسخ اليومية التلقائية، ومعها نسخة يدوية قبل كل migration.

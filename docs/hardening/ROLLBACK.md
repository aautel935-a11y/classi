# خطة التراجع (Rollback) — فرع hardening/production-readiness

## ترتيب النشر (عند الموافقة)
1. **نسخة احتياطية قبل أي شيء**:
   - من Supabase: Database → Backups.
   - أو بالأمر `supabase db dump -f backup-YYYYMMDD.sql`، باتصال الإنتاج الخاص بك.
   - احفظ الملف خارج الحاسوب.
2. **تطبيق الـ migration على Staging أولاً:**
   - الملف: `supabase/migrations/20261031000000_production_hardening.sql`.
   - ثم تشغيل اختبارات E2E على Staging.
3. **تطبيقها على الإنتاج** (محرر SQL). مدة متوقعة: ثوانٍ.
   - الجداول صغيرة، والقيود الجديدة `NOT VALID` لا تفحص الصفوف القديمة.
4. **نشر كود التطبيق** (دمج الفرع في `main`).

لماذا هذا الترتيب؟ القاعدة الجديدة متوافقة مع كود التطبيق الحالي، فالمسارات القديمة تعمل وتحصل على رسائل رفض عربية حيث مُنعت الإساءة. أما الكود الجديد فيعتمد على دوال جديدة، مثل `my_staff_invites` و`my_link_requests`. لو نُشر الكود قبل القاعدة لبقيت هذه الأقسام فارغة فقط، دون أن تنكسر الصفحات.

## التراجع عن الكود
في Vercel، اختر Deployments، ثم آخر نشر سليم قبل الدمج، ثم **Instant Rollback**. لا يمسّ هذا القاعدة.

## التراجع عن القاعدة

### أ. تراجع جزئي فوري: يُنفَّذ في محرر SQL ولا يحتاج نسخة احتياطية

| العَرَض بعد النشر | التراجع |
|---|---|
| صفحة أو ميزة تعطي `permission denied for function X` | `grant execute on function public.X to authenticated;` (أو `anon` للصفحات العامة). بعدها أضف الدالة إلى القائمة في migration جديد |
| تراجع كامل عن قائمة الصلاحيات (SEC-01) | `grant execute on all functions in schema public to anon, authenticated;` |
| سقف SMS اليومي صغير | `insert into app_settings(key,value) values ('sms_daily_cap_per_user','10') on conflict (key) do update set value=excluded.value;` (والمفتاح `sms_daily_cap` للسقف العام، الافتراضي 400) |
| حدّ الحجوزات المفتوحة لكل عرض (الافتراضي 8) | المفتاح `max_open_bookings_per_offer` بالطريقة نفسها |
| حدّ رموز الدخول (5 في الساعة، 15 في اليوم) | المفتاحان `otp_per_hour` و`otp_per_day` |
| حدّ دعوات الطاقم (10 يومياً) | المفتاح `staff_invites_per_day` |
| حجز صحيح يُرفض بسبب ساعات المعلم | `drop trigger bookings_zzz_rules on public.bookings;` (يلغي القواعد الأربع معاً: ساعات المعلم، الحد الأعلى، تكرار المقعد، طريقة الدفع) |
| معلم موقوف يجب أن يكمل عملاً | فكّ الإيقاف من لوحة الأدمن. التعطيل العام للحماية: `drop trigger <table>_active_writer on public.<table>;` |

### ب. تراجع كامل
استعادة النسخة الاحتياطية من الخطوة 1. تُفقد أي بيانات كُتبت بعد النشر، لذلك تُستخدم فقط إن فشل التراجع الجزئي.

## ما يمنع النشر التلقائي من هذا الفرع
- **الفرع لم يُرفع إلى GitHub.** كل الـ commits محلية. Vercel ينشر تلقائياً كل فرع يُرفع، كمعاينة (Preview)، ومتغيرات البيئة قد تكون مشتركة مع الإنتاج. لذلك لن يُرفع الفرع إلا بموافقتك.
- **الـ migrations لا تُطبَّق من هنا.** لا يوجد اتصال بقاعدة الإنتاج، ولا Supabase CLI مرتبط. كل الاختبارات جرت على Postgres محلي.

## اختبار خطة التراجع
- **ما جُرّب محلياً:**
  1. بناء القاعدة بلا الـ migration الجديدة (النسخة الحالية)، ثم معها.
  2. الاختبارات تُظهر الفرق قبل وبعد.
  3. أوامر التراجع الجزئي جُرّبت على قاعدة محلية:
     - `grant execute on all functions…` يعيد الوضع السابق؛
     - `drop trigger bookings_zzz_rules` يلغي قواعد الحجز الأربع.
- **ما لم يُجرَّب:** استعادة نسخة احتياطية حقيقية من Supabase. لا وصول للإنتاج من هنا، وهي خطوة مطلوبة قبل الإطلاق (انظر تقرير الجاهزية).
